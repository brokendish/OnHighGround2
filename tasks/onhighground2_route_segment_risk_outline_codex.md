# OnHighGround2 ルート危険区間アウトライン表示 検証指示書（CODEX向け）

## 目的

Claude Code 実装後、ルート危険区間アウトライン表示が既存機能を壊さず、設計どおりに動作していることを検証する。

本機能は、候補ルート色を維持したまま、危険状態を外枠で表示する。

```text
通常区間   ：ベースルート色のみ
注意予告   ：ベースルート色 + 黄色アウトライン
危険区間   ：ベースルート色 + 赤色アウトライン
復帰注意   ：ベースルート色 + 黄色アウトライン
```

## 検証対象

主に以下を確認する。

- ルート表示
- 候補ルート切替
- route risk scoring
- ハザード重なり区間の表示
- スマホ表示
- 既存回帰

対象ファイルは実装差分から判断すること。

## 事前確認

以下を確認する。

```bash
git status
```

必要に応じて以下を確認する。

```bash
docker compose ps
curl -s http://localhost:8000/api/health || true
curl -s http://localhost:8080/tiles/catalog | head || true
```

プロジェクトの実際の compose / port 設定に合わせて調整すること。

## 静的確認

### 1. 差分確認

```bash
git diff --stat
git diff
```

確認観点:

- ルート描画処理が過剰に作り替えられていない
- 既存 route risk scoring が壊されていない
- 候補ルート UI が壊されていない
- デバッグログが過剰に残っていない
- ハードコードが多すぎない

### 2. JavaScript 構文確認

既存の確認方法があればそれを優先する。

例:

```bash
node --check frontend/js/navigation.js
```

複数ファイルに分かれている場合は、変更された JS をすべて確認する。

```bash
find frontend -name '*.js' -print0 | xargs -0 -n1 node --check
```

ただしブラウザ専用構文や import 事情で失敗する場合は、既存プロジェクトの検証方法を優先する。

## API確認

### 1. route-risk API が壊れていないこと

既存の `/api/route-risk` 呼び出し方法に合わせて確認する。

確認項目:

- 200 が返る
- `safety_score` がある
- `risk_level` がある
- `risk_summary` がある
- ハザード別の通過率または説明が返る
- スコアが `0〜100` に収まる

### 2. 失敗時のフォールバック

route-risk API が失敗しても、通常ルート描画が壊れない設計になっていることを確認する。

可能であれば一時的に API 失敗を mock し、以下を確認する。

- ルート線は表示される
- アウトラインは表示されない、または安全側に非表示
- JS エラーで画面全体が止まらない

## E2E / ブラウザ確認

Playwright など既存の E2E があれば実行する。

```bash
npx playwright test
```

全件が重い場合は、ルート表示・ナビ・候補切替に関係するテストを優先する。

## 手動表示確認

### 1. 危険区間ありルート

洪水または低地・排水困難エリアを通るルートを作成する。

確認項目:

- 候補ルート本体色が維持される
- 危険区間に赤アウトラインが出る
- 危険区間の手前に黄色アウトラインが出る
- 危険区間の直後に黄色アウトラインが出る
- 赤が黄色で上書きされていない
- 現在地マーカーを隠していない
- 目的地マーカーを隠していない
- 地図背景が読める

### 2. 危険区間なしルート

ハザードと重ならないルートを作成する。

確認項目:

- 通常ルート表示になる
- 不要な黄色/赤アウトラインが出ない
- risk summary が安全側の場合、表示と矛盾しない

### 3. 候補ルート切替

候補1、候補2、候補3を切り替える。

確認項目:

- 選択中ルートのアウトラインだけが目立つ
- 非選択ルートに過剰なアウトラインが出ない
- 切替後に古いアウトラインが残らない
- 候補色とアウトライン色の関係が破綻しない

### 4. ハザードレイヤー OFF 時

洪水・低地などのレイヤー表示を OFF にした状態で確認する。

確認項目:

- route risk scoring 結果に基づくアウトラインは表示される
- ハザードレイヤー OFF でも JS エラーが出ない
- UI上の意味が破綻しない

### 5. ハザードレイヤー ON 時

洪水・低地などのレイヤー表示を ON にした状態で確認する。

確認項目:

- ハザード面とルートアウトラインが重なっても視認できる
- 赤アウトラインがハザード色に埋もれない
- 黄色アウトラインが地図背景に埋もれない

## スマホ表示確認

スマホ幅で確認する。

確認項目:

- 線が太すぎない
- ボトムパネルと干渉しない
- 現在地周辺でルート状態が見える
- ピンチ・ドラッグ操作で描画が破綻しない
- iPhone Safari 相当の狭い画面でも読める

## パフォーマンス確認

確認項目:

- ルート表示時に明らかなフリーズがない
- 地図パン時に極端に重くならない
- 候補切替時に古い layer が残り続けない
- 再ルートを繰り返しても layer が増殖しない

可能であれば DevTools で Leaflet layer 数やメモリ増加を確認する。

## 回帰確認

以下の既存機能に影響がないことを確認する。

- 現在地表示
- 目的地表示
- ルート候補表示
- ルート選択 UI
- route risk summary 表示
- safety_score 表示
- risk_level 表示
- ハザードレイヤー ON/OFF
- 避難所表示
- 地震タブ表示
- ナビ開始
- 再ルート
- 目的地到着判定

## 期待される最終判定

以下を満たす場合は PASS とする。

- 危険区間が赤アウトラインで見える
- 危険区間の前後が黄色アウトラインで見える
- 候補ルート色が維持されている
- 候補切替で表示が破綻しない
- route risk API 失敗時も通常ルート表示が壊れない
- スマホ表示で実用上問題ない
- 既存主要機能の回帰がない

軽微な表示調整のみ残る場合は `PASS with notes` とする。

例:

```text
PASS with notes
- 黄色アウトラインが一部背景に埋もれやすい
- スマホでは danger outline weight を少し下げた方がよい
```
