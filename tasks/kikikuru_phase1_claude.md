# Claude Code向け実装指示書: キキクル Phase 1 表示レイヤー追加

## 目的
OnHighGround2 に気象庁キキクル（危険度分布）の表示レイヤーを追加する。
Phase 1 では、ルート危険度スコアやナビ判定にはまだ組み込まず、地図上でリアルタイム危険度を確認できる状態を作る。

## 対象優先順位
1. 浸水キキクル
2. 洪水キキクル
3. 土砂キキクル

まずは浸水キキクルを最優先で実装する。
浸水キキクルの実装で、取得方式・キャッシュ・レイヤー管理・凡例・ON/OFF UI・エラー表示の基本形を作り、洪水・土砂へ横展開できる構造にする。

## 前提
- キキクルは固定ハザードではなくリアルタイム危険度情報として扱う。
- 既存の洪水・津波・土砂・低地・排水困難エリア等の固定レイヤーとは意味が違うため、UI上でも「現在の危険度」と分かる表現にする。
- 取得失敗・更新停止・未対応ズーム・データなしを `none` と混同しない。
- stale / unknown / unavailable を明確に区別する。
- Phase 1 では判定ロジックへ組み込まない。

## 調査
実装前に、現在の気象庁キキクルページで使用されている以下を確認する。

- 浸水キキクルのタイルURLまたはデータURL
- 洪水キキクルのタイルURLまたはデータURL
- 土砂キキクルのタイルURLまたはデータURL
- 時刻管理ファイルの有無
- 更新間隔
- minZoom / maxZoom
- タイルの色・透明度・マスクの扱い
- CORS / referer / キャッシュヘッダの挙動

調査結果は `tasks/kikikuru_phase1_investigation.md` に記録する。

## 実装方針
### 1. フロントエンド中心で開始
Phase 1 は、可能であれば Leaflet の TileLayer としてフロント側に実装する。
ただし、CORS・URL安定性・キャッシュ・利用上の都合で直接参照が不安定な場合は、バックエンドプロキシ方式に切り替える。

### 2. レイヤー構成
新規 JS ファイルを追加する。

候補:
- `frontend/js/kikikuru-layer.js`
- `frontend/js/kikikuru-control.js`

既存構成に合わせて、必要なら1ファイルにまとめてもよい。

レイヤーID案:
- `kikikuru_inundation`
- `kikikuru_flood`
- `kikikuru_landslide`

表示名案:
- `浸水キキクル`
- `洪水キキクル`
- `土砂キキクル`

### 3. UI
既存のハザード表示UIまたは気象カードの近くに、キキクル専用のON/OFF UIを追加する。

最低限必要なUI:
- 浸水キキクル ON/OFF
- 洪水キキクル ON/OFF（未実装なら disabled でも可）
- 土砂キキクル ON/OFF（未実装なら disabled でも可）
- 最終更新時刻
- 取得状態
  - 正常
  - 更新確認中
  - 取得不可
  - データなし
  - 情報が古い可能性あり

### 4. 凡例
キキクルの危険度凡例を追加する。

扱う危険度:
- 災害切迫
- 危険
- 警戒
- 注意
- 今後の情報等に留意
- 表示なし / データなし
- 取得不可 / 判定不能

色は可能な限り気象庁の表示に寄せる。
ただし、既存ハザード色と混同しないよう、凡例には必ず「キキクル（現在の危険度）」と明記する。

### 5. キャッシュ・更新
- キキクルはリアルタイム情報なので、ブラウザキャッシュで古い表示が残らないようにする。
- 更新確認は手動更新または一定間隔更新に対応できる構造にする。
- 初期実装では過度なポーリングを避ける。
- 最終更新時刻をUIに出す。
- 古い情報のまま表示している可能性がある場合は stale 表示にする。

### 6. 既存レイヤーとの関係
- 既存の固定ハザードレイヤーとは独立したON/OFFにする。
- 固定ハザードとキキクルを同時表示できるようにする。
- 透明度を調整し、地図・避難所・ルートが読めなくならないようにする。
- キキクル表示中も避難所マーカー・現在地・ルート・危険区間表示を潰さない。

### 7. バックエンドプロキシが必要な場合
必要に応じて以下のAPIを追加する。

- `GET /api/weather/kikikuru/layers`
- `GET /api/weather/kikikuru/status`
- `GET /api/weather/kikikuru/tile/{kind}/{z}/{x}/{y}.png`

`kind` は以下を想定する。
- `inundation`
- `flood`
- `landslide`

バックエンドで実装する場合は、以下を満たすこと。
- 外部URLをフロントにベタ書きしすぎない
- TTL付きキャッシュを入れる
- 取得失敗時は適切なHTTPステータスとJSONエラーを返す
- stale/unknown/none を混同しない
- ログに取得URL・ステータス・経過時間・キャッシュヒットを出す

### 8. 既存コードへの影響
- 既存の雨量レーダー、気象カード、ハザードレイヤー、避難所マーカー、ルート表示を壊さない。
- `typeof` ガードや存在チェックを入れ、キキクル側の失敗で画面全体が落ちないようにする。
- 初期表示でキキクルを自動ONにしない。まずはユーザー操作でONにする。

## 実装完了条件
- 浸水キキクルを地図上に表示できる。
- ON/OFFができる。
- 最終更新時刻または取得状態が表示される。
- 凡例が表示される。
- 取得失敗時に画面が壊れない。
- 既存の主要レイヤー・避難所・ルート表示が壊れない。
- 洪水・土砂へ横展開しやすい構造になっている。

## 非対応範囲
Phase 1 では以下は実装しない。

- 現在地周辺の危険度要約
- 目的地周辺の危険度要約
- ルート危険度スコアへの加点
- ナビ中の迂回提案
- 自動ルート変更
